About bulk mode
Bulk mode: steps through your sidebar matches automatically instead of one profile at a time — 15 per run by default, real randomised delays (10–60s) between each, remembered on Tinder's own site so the next run (later today or tomorrow) only picks up whoever's left. Fine to run a few times a day at that pace, or a large number left overnight — e.g. tinderBulkImport(250). Pasting the snippet only defines it; run it with tinderBulkImport() in the console for the default 15, or tinderBulkImport(30) for a custom size — no need to re-paste to change it. Every 25 profiles it checkpoints to its own downloaded file, so a crash, sleep or closed tab partway through an overnight run only loses the last (incomplete) chunk, not the whole night. The dashboard's file picker below takes several of those files at once — select them all and it sorts anyone it already knows for certain into a bulk-review list (photos, name, and what's new, tick the ones that look right and submit together) and only routes genuinely new or uncertain matches to the one-by-one reviewer. This runs unattended across many real profiles in a row — if you see anything that looks like a rate limit or a verification prompt, stop and give it a break. A slide that's a short video clip (not just a photo) is captured too — its poster still goes in with the photos, the clip itself imports as a playable attachment on the connection. If you ever notice a match that never made it into the dashboard (an early run can scrape a profile while its panel hasn't finished loading, mark it done, and never send it on), run tinderFindMissing() after a full scroll of both lists — it compares your whole match list against what the dashboard already has (ignoring this browser's skip-list) and prints a ready tinderReextract([...]) call for anyone missing.

// CORRECTION to this function's own former claim ("both lists are always
// in the DOM at once, verified against a real saved page with both tabs
// captured"): that was true of a STATIC SAVED HTML capture, which
// preserves whatever markup existed at save time regardless of
// visibility -- but confirmed live, in the actual running app, only the
// CURRENTLY ACTIVE tab's <ul> is ever mounted at all; switching tabs
// swaps which one exists in the DOM, it doesn't just show/hide both. So
// this only ever reads whichever ONE of Matches/Messages is currently
// selected -- every caller that genuinely needs the full combined set
// uses collectAllCandidates() below instead, which switches tabs itself.
// Kept as the cheap, no-navigation building block for callers that only
// need a fast sanity check against whatever's already showing.
function collectCandidates() {
  const seen = new Set();
  const rows = [];
  const grab = (ul) => {
    if (!ul) return;
    ul.querySelectorAll('li a[href*="/app/messages/"]').forEach((a) => {
      const m = a.href.match(/\/app\/messages\/([a-zA-Z0-9]+)/);
      if (!m) return;
      const id = m[1];
      if (seen.has(id)) return;
      seen.add(id);
      const name = (a.getAttribute('aria-label') || '').replace(/\.\s*Start chat\.?$/i, '').trim();
      rows.push({ id, name, href: a.href });
    });
  };
  grab(document.querySelector('ul[aria-label="Your recent messages"]'));
  grab(document.querySelector('ul[aria-label="Your matches"]'));
  return rows;
}

// The real tab buttons (confirmed live against the actual markup, a
// standard ARIA tablist: role="tab" buttons with aria-selected, not just
// styled links) -- selected by visible text rather than their id
// attributes, which look auto-generated and aren't safe to hardcode.
function findTabButton(label) {
  return [...document.querySelectorAll('[role="tab"]')].find((b) => b.textContent.trim().startsWith(label));
}

// Clicks a tab and waits for it to actually take effect -- aria-selected
// flips as soon as the click handler runs, but the new tab's own content
// still needs a moment to actually mount, so a short settle delay follows
// the flip rather than treating aria-selected alone as "ready".
async function switchToTab(label) {
  const tab = findTabButton(label);
  if (!tab) return false;
  if (tab.getAttribute('aria-selected') !== 'true') {
    tab.click();
    for (let i = 0; i < 20 && tab.getAttribute('aria-selected') !== 'true'; i++) {
      await new Promise((r) => setTimeout(r, 100));
    }
  }
  await new Promise((r) => setTimeout(r, 400));
  return true;
}

// The actual fix for the "only ever sees one tab" problem above: switches
// to Matches, reads it, switches to Messages, reads that too, merges by
// id, then returns to whichever tab was active when called so the
// visible UI ends up where it started. Costs a couple of tab-switches
// (roughly a second) -- worth it here, where completeness genuinely
// matters and a real extraction is about to happen anyway, but NOT baked
// into collectCandidates() itself, which stays instant for callers that
// don't need it.
async function collectAllCandidates() {
  const originalTab = findTabButton('Matches')?.getAttribute('aria-selected') === 'true' ? 'Matches'
    : findTabButton('Messages')?.getAttribute('aria-selected') === 'true' ? 'Messages' : null;
  const seen = new Set();
  const rows = [];
  const grabInto = () => {
    collectCandidates().forEach((row) => {
      if (seen.has(row.id)) return;
      seen.add(row.id);
      rows.push(row);
    });
  };
  await switchToTab('Matches');
  grabInto();
  await switchToTab('Messages');
  grabInto();
  if (originalTab) await switchToTab(originalTab);
  return rows;
}

// Re-finds a row's link fresh at click time, by match id rather than by
// comparing href strings — confirmed live: `a.href` (the JS
// property, always browser-resolved to an absolute URL) doesn't
// necessarily equal the raw href ATTRIBUTE Tinder's live DOM actually
// carries, so `document.querySelector('a[href="' + resolvedUrl + '"]')`
// failed to find a person visibly on screen. Matching on the id parsed
// out of the live `.href` property on both sides (same parsing
// collectCandidates already does) sidesteps that mismatch entirely. Tries
// the currently active tab first (free, no navigation) -- only if that
// misses does it switch to the other tab and try again, since a row
// collected via collectAllCandidates() could belong to either one.
async function findLinkById(id) {
  const tryCurrent = () => {
    for (const ul of [document.querySelector('ul[aria-label="Your recent messages"]'), document.querySelector('ul[aria-label="Your matches"]')]) {
      if (!ul) continue;
      const found = [...ul.querySelectorAll('li a[href*="/app/messages/"]')].find((a) => {
        const m = a.href.match(/\/app\/messages\/([a-zA-Z0-9]+)/);
        return m && m[1] === id;
      });
      if (found) return found;
    }
    return null;
  };
  const first = tryCurrent();
  if (first) return first;
  const otherTab = findTabButton('Matches')?.getAttribute('aria-selected') === 'true' ? 'Messages' : 'Matches';
  await switchToTab(otherTab);
  return tryCurrent();
}

// Polls the profile panel until it's actually showing the person just
// clicked, rather than a fixed delay — SPA navigation time varies,
// and a fixed wait is either too short sometimes or wastefully long
// every time.
async function waitForProfile(expectedName, timeoutMs) {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    const h1 = document.querySelector('#main-content h1[aria-label]');
    const label = h1 ? (h1.getAttribute('aria-label') || '') : '';
    if (label && label.toLowerCase().startsWith(expectedName.toLowerCase())) return true;
    await new Promise((r) => setTimeout(r, 250));
  }
  return false;
}

// Cross-day memory lives on Tinder's own origin, not the dashboard's --
// the two sites can't see each other, so this is the only way a later
// run knows what an earlier one already covered. Keyed by match id, the
// same permanent identifier the URL itself uses.
//
// Version-stamped rather than a flat done/not-done flag: a plain flag
// can never be revisited once a bug in the extraction itself is found
// and fixed (confirmed live: a photo-scope change broke photo capture
// entirely for a while) -- anyone scraped during that window would stay
// marked done forever, missing photos, with no way back short of
// wiping ALL tracking and re-running everyone. Bump SCRIPT_VERSION
// whenever a fix could affect what gets captured; anyone stamped with
// an older version is automatically re-offered next run. Re-running
// someone already saved is safe either way -- the dashboard fills in
// whatever's still missing rather than duplicating what's already
// there.
const SCRIPT_VERSION = 9; // captured photo URLs had their resolution prefix force-rewritten to "640x800_", which 403s for any photo Tinder didn't natively crop to that size -- confirmed live (640x640 photo: 200 OK unmodified, 403 once rewritten to 640x800). Now keeps the exact URL actually rendered live.
const DONE_KEY = 'dashTinderBulkDone';
const MIN_DELAY_MS = 10000, MAX_DELAY_MS = 60000; // randomised, not a fixed interval — a fixed gap is a bot tell

function loadDoneVersions() {
  let doneVersions = {};
  try {
    const raw = JSON.parse(localStorage.getItem(DONE_KEY) || '{}');
    if (Array.isArray(raw)) {
      // Legacy format from before version-stamping existed: a flat array
      // of ids with no version attached. Every one of these could have
      // been scraped under the exact bug this versioning exists to
      // recover from, so treat them all as version 0 -- older than any
      // real version -- and let them be re-offered.
      raw.forEach((id) => { doneVersions[id] = 0; });
    } else {
      doneVersions = raw || {};
    }
  } catch (e) { doneVersions = {}; }
  return doneVersions;
}
function saveDoneVersions(doneVersions) { localStorage.setItem(DONE_KEY, JSON.stringify(doneVersions)); }
function isDoneWith(doneVersions, id) { return (doneVersions[id] || 0) >= SCRIPT_VERSION; }

// Writes whatever's in `list` to its own downloaded file, optionally also
// the clipboard. `state` ({chunkIndex, totalSaved}) belongs to the
// caller, not a shared counter here -- tinderBulkImport() and
// tinderCatchUp() each track their own run's numbering independently, so
// one doesn't pick up a count left over from the other. `filePrefix`
// (default 'tinder-batch') lets the stale-profile sweep below save to a
// visibly different filename in Downloads rather than mixing in with a
// run's own primary output -- it's a distinct, no-rush batch, not part of
// the count the primary task reports.
function downloadChunk(list, copyToClipboard, state, filePrefix) {
  if (!list.length) return;
  state.chunkIndex++;
  state.totalSaved += list.length;
  const json = JSON.stringify({ profiles: list }, null, 1);
  let copied = false;
  if (copyToClipboard) {
    try { copy(json); copied = true; } catch (e) { /* not in a real DevTools console */ }
    if (!copied) { try { navigator.clipboard.writeText(json); copied = true; } catch (e) { /* no clipboard permission/focus */ } }
  }
  try {
    const blob = new Blob([json], { type: 'application/json' });
    const url = URL.createObjectURL(blob);
    const a = document.createElement('a');
    a.href = url;
    a.download = `${filePrefix || 'tinder-batch'}-${new Date().toISOString().replace(/[:.]/g, '-')}-part${state.chunkIndex}.json`;
    document.body.appendChild(a);
    a.click();
    a.remove();
    setTimeout(() => URL.revokeObjectURL(url), 10000);
    console.log(`Checkpoint: ${list.length} profile${list.length === 1 ? '' : 's'} saved to part${state.chunkIndex} in Downloads (${state.totalSaved} total so far)${copied ? ' -- also on the clipboard' : ''}.`);
  } catch (e) {
    console.warn(`Checkpoint download blocked for part${state.chunkIndex} -- ${list.length} profiles only exist in this tab's memory right now, keep it open.`);
  }
}

// Squaring the random factor skews toward the low end of the range
// instead of a flat spread -- long, near-60s waits get rarer while the
// occasional real one still happens (still not a fixed gap, still not a
// bot tell), cutting ~24% off the average total wait versus a uniform
// pick across the same 10-60s bounds.
async function randomDelay() {
  const delay = MIN_DELAY_MS + Math.pow(Math.random(), 2) * (MAX_DELAY_MS - MIN_DELAY_MS);
  console.log(`Waiting ${Math.round(delay / 1000)}s...`);
  await new Promise((r) => setTimeout(r, delay));
}

window.tinderBulkImport = async (batchSize, staleBatchSize) => {
  const BATCH_SIZE = batchSize || 15; // "10-20 or so per day" — override per-call: tinderBulkImport(30), or tinderBulkImport(250) left running overnight
  const CHUNK_SIZE = 25; // checkpoint to its own downloaded file this often -- a long unattended run surviving a sleep/crash/closed-tab partway through loses at most this many, not the whole run, and each file is pasteable into the dashboard as soon as it lands rather than waiting for the end

  const doneVersions = loadDoneVersions();
  const emptyMisses = loadEmptyMisses();
  const candidates = await collectAllCandidates();
  const todo = candidates.filter((r) => !isDoneWith(doneVersions, r.id)).slice(0, BATCH_SIZE);
  const profiles = [];
  const chunkState = { chunkIndex: 0, totalSaved: 0 };

  // Always logged, whether or not there's anything new to actually run --
  // "how far through 205 am I" shouldn't require sitting through another
  // batch to find out.
  const doneCount = candidates.filter((r) => isDoneWith(doneVersions, r.id)).length;
  console.log(`${candidates.length} visible in the sidebar -- ${doneCount} already done, ${candidates.length - doneCount} remaining.`);

  // "Nothing new" no longer returns early -- it still falls through to the
  // stale-refresh tail below. Once everyone visible has been imported at
  // least once (the steady state most runs actually hit), the "new
  // matches" loop has nothing to do every single time -- an early return
  // here would silently skip the stale sweep on almost every run, which
  // defeats the point of it running automatically at all.
  if (!todo.length) {
    console.log(`Nothing new -- all visible matches already processed. Scroll the list down to reveal more, then run again.`);
  } else {
  console.log(`Processing ${todo.length} new match${todo.length === 1 ? '' : 'es'}. This takes a while -- real delays are the point.`);
  // Wrapped in try/finally so a crash partway through still outputs and
  // copies whatever WAS gathered, rather than losing a run's worth of
  // waiting to one bad profile.
  try {
    for (let i = 0; i < todo.length; i++) {
      const row = todo[i];
      console.log(`[${i + 1}/${todo.length}] ${row.name}...`);
      const link = await findLinkById(row.id);
      if (!link) { console.warn(`Couldn't find ${row.name} any more -- the sidebar re-rendered. Stopping here.`); break; }
      link.click();
      const loaded = await waitForProfile(row.name, 8000);
      if (!loaded) {
        console.warn(`${row.name}'s profile didn't load in time -- skipped, will retry next run.`);
        continue;
      }
      await new Promise((r) => setTimeout(r, 500));
      try {
        const extracted = await extractProfile(row.name);
        // Zero photos on an extract that didn't throw = the panel wasn't
        // rendered when it was read (a real profile always has ≥1
        // photo). Leave it un-done so next run retries it -- unless it's
        // failed this way EMPTY_MISS_GIVE_UP runs running, in which case
        // it's genuinely stuck (e.g. a deleted-account match card) and
        // gets marked done so it can't loop forever.
        if (!extracted.photos.length) {
          emptyMisses[row.id] = (emptyMisses[row.id] || 0) + 1;
          if (emptyMisses[row.id] >= EMPTY_MISS_GIVE_UP) {
            console.warn(`${row.name}: still no photos after ${emptyMisses[row.id]} tries -- giving up, marking done.`);
            doneVersions[row.id] = SCRIPT_VERSION;
            saveDoneVersions(doneVersions);
          } else {
            console.warn(`${row.name}: no photos captured -- panel likely not loaded, will retry next run.`);
          }
          saveEmptyMisses(emptyMisses);
        } else {
          // Photos but no fields is a real bare match -- still worth
          // capturing for the photos alone, which the review screen shows.
          extracted.matchId = row.id; // already known from the sidebar row — same permanent id the single-profile snippet reads from the URL
          profiles.push(extracted);
          if (profiles.length >= CHUNK_SIZE) downloadChunk(profiles.splice(0, profiles.length), false, chunkState);
          doneVersions[row.id] = SCRIPT_VERSION;
          saveDoneVersions(doneVersions);
          if (emptyMisses[row.id]) { delete emptyMisses[row.id]; saveEmptyMisses(emptyMisses); }
        }
      } catch (err) {
        console.warn(`Extraction failed for ${row.name}: ${err.message} -- skipped.`);
      }
      if (i < todo.length - 1) await randomDelay();
    }
  } finally {
    // Marked done in localStorage the moment a profile is scraped here,
    // not when the dashboard actually saves it -- the two are different
    // origins with no way to signal back. So the clipboard alone isn't
    // enough: closing the tab, or the clipboard getting overwritten,
    // before pasting would lose this batch for good even though it's
    // already marked as never-offer-again. A real file on disk survives
    // that -- still there to paste in later even if today's paste never
    // happens. Whatever's left in `profiles` here is the tail end that
    // hasn't hit a CHUNK_SIZE checkpoint yet -- everyone else already has
    // their own file, downloaded as the run went.
    downloadChunk(profiles, true, chunkState);
    console.log(`${chunkState.totalSaved} of ${todo.length} attempted profile${todo.length === 1 ? '' : 's'} extracted, across ${chunkState.chunkIndex} file${chunkState.chunkIndex === 1 ? '' : 's'} in your Downloads folder. Paste them into the dashboard now or later -- the file picker there takes several at once.`);
  }
  }
  // Runs after the primary task either way (nothing new, a clean finish,
  // or a crash partway through) -- its own separate, no-rush file. See
  // staleSweepTail's own comment.
  await staleSweepTail(staleBatchSize ?? 25);
};

// Re-checks people ALREADY captured for new activity since a given date,
// instead of only ever picking up brand-new matches like
// tinderBulkImport() does -- someone marked done there is never
// revisited again even after a new message arrives. Built on an
// assumption about Tinder's own sidebar order, per the request that
// prompted this: the Messages tab is sorted by last-message-date, newest
// first, and the Matches tab by match-date, newest first —
// unverified against a real long list, since no captured page has had
// one to check.
//
// Two genuinely different questions, not one applied twice:
//
// Matches = "is this a profile I've never indexed at all?" A match with
// no chat yet has no reliable date signal on the row itself to compare
// against anything -- presence in doneVersions (seen it before, yes/no)
// IS the only signal, so this sweeps with `floor` pinned to EPOCH
// ("date zero") and never even reads a date field: an already-indexed
// match is skipped WITHOUT opening it at all (nothing new a plain
// re-index would find), stopping once several in a row turn out
// already-known. This only ever catches brand-new matches -- it does
// NOT re-check an old match's profile for edits (bio/photos changed with
// no message sent) or notice an unmatch; see the note below on why.
//
// Messages = "does this conversation (new OR already-known) have
// activity since `since`?" Once two people exchange even one message,
// Tinder moves that row here and it carries both the profile AND the
// chat -- so this is also where a profile edit on an already-known match
// would actually surface, IF they've messaged at all. Every row gets
// reopened here, including already-done ones (that's the whole point),
// reading the real "Last message date" and stopping the first time it's
// older than `since`.
//
// Both run through the one sweep() below, just anchored to a different
// floor (EPOCH vs a real date) -- not two copies of the same logic.
//
// Not done: detecting an UNMATCH (someone vanishes from the Matches
// list entirely) needs a full walk of the current list diffed against
// everyone already known as matched -- worth doing once, as a distinct
// tracked attribute, but not worth the weekly cost of walking the whole
// list just for that, so this sweep keeps its early-stop rather than
// running Matches to completion every time.
//
// Either sweep can also hit a safety cap before running out of rows -- a
// guard against the sort-order assumption turning out wrong for some
// account or view. A loud, bounded stop ("hit the cap") beats silently
// missing everything past a wrongly-ordered entry.
window.tinderCatchUp = async (sinceDate, batchSize, staleBatchSize) => {
  const since = String(sinceDate || '').trim();
  if (!/^\d{4}-\d{2}-\d{2}$/.test(since)) {
    console.warn('tinderCatchUp needs a since date like "2026-08-10" -- e.g. tinderCatchUp("2026-08-10")');
    return;
  }
  const EPOCH = '0000-01-01'; // sentinel for "no date signal, presence-only" -- see the Matches note above

  const CAP = batchSize || 40; // per sweep -- see the safety-cap note above
  const doneVersions = loadDoneVersions();
  const emptyMisses = loadEmptyMisses();
  const chunkState = { chunkIndex: 0, totalSaved: 0 };
  const profiles = [];
  const visited = new Set();

  async function processRow(row) {
    const link = await findLinkById(row.id);
    if (!link) return { stop: true, reason: `Couldn't find ${row.name} any more -- the sidebar re-rendered.` };
    link.click();
    const loaded = await waitForProfile(row.name, 8000);
    if (!loaded) { console.warn(`${row.name}'s profile didn't load in time -- skipped.`); return { skip: true }; }
    await new Promise((r) => setTimeout(r, 500));
    try {
      return { extracted: await extractProfile(row.name) };
    } catch (err) {
      console.warn(`Extraction failed for ${row.name}: ${err.message} -- skipped.`);
      return { skip: true };
    }
  }

  function rowsFrom(ul) {
    return (ul ? [...ul.querySelectorAll('li a[href*="/app/messages/"]')] : []).map((a) => {
      const m = a.href.match(/\/app\/messages\/([a-zA-Z0-9]+)/);
      if (!m) return null;
      return { id: m[1], name: (a.getAttribute('aria-label') || '').replace(/\.\s*Start chat\.?$/i, '').trim() };
    }).filter(Boolean);
  }

  function keep(row, extracted) {
    // Same "zero photos = not rendered, not empty" rule as
    // tinderBulkImport -- see loadEmptyMisses()'s own comment.
    if (!extracted.photos.length) {
      emptyMisses[row.id] = (emptyMisses[row.id] || 0) + 1;
      if (emptyMisses[row.id] >= EMPTY_MISS_GIVE_UP) {
        console.warn(`${row.name}: still no photos after ${emptyMisses[row.id]} tries -- giving up, marking done.`);
        doneVersions[row.id] = SCRIPT_VERSION;
        saveDoneVersions(doneVersions);
      } else {
        console.warn(`${row.name}: no photos captured -- panel likely not loaded, will retry next run.`);
      }
      saveEmptyMisses(emptyMisses);
      return;
    }
    extracted.matchId = row.id;
    profiles.push(extracted);
    if (profiles.length >= 25) downloadChunk(profiles.splice(0, profiles.length), false, chunkState);
    doneVersions[row.id] = SCRIPT_VERSION;
    saveDoneVersions(doneVersions);
    if (emptyMisses[row.id]) { delete emptyMisses[row.id]; saveEmptyMisses(emptyMisses); }
  }

  // One sweep, used for both tabs -- see the comment above the function
  // for what `floor` (a real date, or EPOCH) actually changes.
  async function sweep(label, ul, dateFieldLabel, floor) {
    const rows = rowsFrom(ul);
    console.log(`${label}: ${rows.length} visible, scanning from the top for activity since ${floor === EPOCH ? 'the beginning' : floor}...`);
    let n = 0;
    let consecutiveDone = 0;
    for (const row of rows) {
      if (visited.has(row.id)) continue;
      if (floor === EPOCH && isDoneWith(doneVersions, row.id)) {
        consecutiveDone++;
        if (consecutiveDone >= 5) { console.log(`${label}: 5 already-known in a row -- stopping (list is date-sorted, so the rest are presumably older too).`); break; }
        continue;
      }
      consecutiveDone = 0;
      if (n >= CAP) { console.log(`${label}: hit the safety cap of ${CAP} -- stopping here.`); break; }
      n++;
      visited.add(row.id);
      console.log(`${label} [${n}] ${row.name}...`);
      const result = await processRow(row);
      if (result.stop) { console.warn(result.reason); break; }
      if (!result.skip) {
        if (floor === EPOCH) {
          keep(row, result.extracted); // brand-new row -- no date gate needed, just keep it
        } else {
          const dateField = result.extracted.fields.find((f) => f.label === dateFieldLabel);
          if (!dateField) {
            console.log(`${row.name}: no ${dateFieldLabel.toLowerCase()} found -- skipped from this pass.`);
          } else if (dateField.value < floor) {
            console.log(`${row.name}: ${dateFieldLabel.toLowerCase()} ${dateField.value}, before ${floor} -- ${label} is date-sorted, so stopping here.`);
            break;
          } else {
            keep(row, result.extracted);
          }
        }
      }
      await randomDelay();
    }
  }

  // Each sweep needs its own tab actually selected first -- confirmed
  // live, only the CURRENTLY ACTIVE tab's <ul> is ever mounted at all
  // (see collectAllCandidates()'s own comment for the fuller story), so
  // computing both <ul>s up front the way this used to would've silently
  // handed the second sweep a null list every time.
  const startedOnTab = findTabButton('Matches')?.getAttribute('aria-selected') === 'true' ? 'Matches'
    : findTabButton('Messages')?.getAttribute('aria-selected') === 'true' ? 'Messages' : null;
  try {
    await switchToTab('Messages');
    await sweep('Messages', document.querySelector('ul[aria-label="Your recent messages"]'), 'Last message date', since);
    await switchToTab('Matches');
    await sweep('Matches', document.querySelector('ul[aria-label="Your matches"]'), null, EPOCH); // dateFieldLabel unused when floor is EPOCH -- see the note above
  } finally {
    if (startedOnTab) await switchToTab(startedOnTab);
    downloadChunk(profiles, true, chunkState);
    console.log(`${chunkState.totalSaved} profile${chunkState.totalSaved === 1 ? '' : 's'} with activity since ${since}, across ${chunkState.chunkIndex} file${chunkState.chunkIndex === 1 ? '' : 's'} in your Downloads folder.`);
    await staleSweepTail(staleBatchSize ?? 25);
  }
};

// A one-off, fast check -- no profile opens, no delays between people,
// since it's just comparing two lists of ids already sitting in the DOM
// (once fully scrolled) against everyone this account has ever indexed.
// Unlike tinderBulkImport()/tinderCatchUp(), completeness genuinely
// matters here: whatever's currently scrolled into view -- or, confirmed
// live, whatever's on the currently ACTIVE TAB at all, Matches and
// Messages are never both mounted at once -- would otherwise look
// identical to a real unmatch. Both tabs get switched to and scrolled to
// the bottom in turn for exactly that reason. Unverified against a real
// long list, since no captured page has had one to check the scroll
// behaviour on.
window.tinderFindUnmatched = async () => {
  // Same "find the nearest real scroll container, not necessarily the
  // list element itself" approach used elsewhere in this snippet, just
  // run to actual completion (scrollHeight stops growing) rather than a
  // fixed number of steps, since there's no known list length to aim for
  // up front the way the whole-profile-panel sweep has.
  async function scrollListFully(ul) {
    if (!ul) return;
    let box = ul;
    while (box && !(box.scrollHeight > box.clientHeight + 50 && box.clientHeight > 100)) box = box.parentElement;
    if (!box) return;
    let lastHeight = -1;
    let stable = 0;
    for (let i = 0; i < 200 && stable < 3; i++) {
      box.scrollTop = box.scrollHeight;
      await new Promise((r) => setTimeout(r, 300));
      if (box.scrollHeight === lastHeight) stable++; else stable = 0;
      lastHeight = box.scrollHeight;
    }
  }

  const startedOnTab = findTabButton('Matches')?.getAttribute('aria-selected') === 'true' ? 'Matches'
    : findTabButton('Messages')?.getAttribute('aria-selected') === 'true' ? 'Messages' : null;
  console.log('Scrolling both lists to load everyone first -- this can take a while for a long history...');
  const currentIds = new Set();
  await switchToTab('Matches');
  await scrollListFully(document.querySelector('ul[aria-label="Your matches"]'));
  collectCandidates().forEach((r) => currentIds.add(r.id));
  await switchToTab('Messages');
  await scrollListFully(document.querySelector('ul[aria-label="Your recent messages"]'));
  collectCandidates().forEach((r) => currentIds.add(r.id));
  if (startedOnTab) await switchToTab(startedOnTab);

  const doneVersions = loadDoneVersions();
  const everKnown = Object.keys(doneVersions);
  const unmatched = everKnown.filter((id) => !currentIds.has(id));

  if (!unmatched.length) {
    console.log(`${currentIds.size} currently visible, ${everKnown.length} ever indexed -- nobody missing.`);
    return;
  }
  const json = JSON.stringify({ unmatched }, null, 1);
  let copied = false;
  try { copy(json); copied = true; } catch (e) { /* not in a real DevTools console */ }
  if (!copied) { try { await navigator.clipboard.writeText(json); copied = true; } catch (e) { /* no clipboard permission/focus */ } }
  console.log(`${unmatched.length} previously-indexed id${unmatched.length === 1 ? '' : 's'} no longer visible in either list -- ${copied ? 'copied' : 'shown below'}. Paste into the dashboard same as any other batch (it only adds a note and a tag, nothing destructive).`);
  if (!copied) console.log(json);
};

// The follow-up to tinderFindUnmatched: its list is only "not in the
// sidebar right now", which a list that didn't fully load looks identical
// to. This looks each of those people up in Tinder's OWN search box by name
// and reports who it can and can't find -- paste the result into the
// dashboard, which clears the ones that are still there and queues the gone
// ones for you to confirm archiving. Takes the people from the dashboard's
// copy of this snippet (window.__dashUnmatched), or pass [{id, name}].
// Before trusting any "gone" it searches for someone who is visibly present
// and stops if the search can't find them, so a search box that behaves
// differently from what's assumed here can't produce false "gone"s.
window.tinderVerifyUnmatched = async (people) => {
  const list = (people || window.__dashUnmatched || []).filter((p) => p && p.id && p.name);
  if (!list.length) { console.warn('Nobody to check -- copy this snippet from the dashboard again (it lists who is flagged Unmatched), or pass [{id, name}].'); return; }
  const wait = (ms) => new Promise((r) => setTimeout(r, ms));
  const SEARCH_SELECTOR = 'input[type="search"], input[placeholder*="earch" i], input[aria-label*="earch" i]';
  const findSearchInput = () => [...document.querySelectorAll(SEARCH_SELECTOR)].find((el) => el.offsetParent !== null) || null;
  // React ignores a plain `.value = ...`; the native setter plus an input
  // event is what it listens for.
  async function setSearch(input, value) {
    const setter = Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set;
    input.focus();
    setter.call(input, value);
    input.dispatchEvent(new Event('input', { bubbles: true }));
  }

  let input = findSearchInput();
  if (!input) {
    const btn = document.querySelector('button[aria-label*="earch" i]');
    if (btn) { btn.click(); await wait(600); input = findSearchInput(); }
  }
  if (!input) {
    const bits = [...document.querySelectorAll('input, button[aria-label*="earch" i], [role="search"]')].slice(0, 12).map((el) => el.outerHTML.slice(0, 220));
    console.warn('Could not find a search box on this page. Paste the lines below back to Claude so the script can be taught Tinder\'s markup:\n' + bits.join('\n'));
    return;
  }

  async function search(name) {
    await setSearch(input, name);
    await wait(1500 + Math.random() * 800);
    return collectCandidates();
  }

  await setSearch(input, '');
  await wait(800);
  const flaggedIds = new Set(list.map((p) => p.id));
  const control = collectCandidates().find((r) => r.name && !flaggedIds.has(r.id));
  if (control) {
    const rows = await search(control.name);
    if (!rows.some((r) => r.id === control.id)) {
      console.warn(`Searching for ${control.name}, who IS in your matches, didn't find them -- so this search can't be trusted to say anyone is gone. Stopped; nothing was checked.`);
      await setSearch(input, '');
      return;
    }
    console.log(`Search works (found ${control.name}). Checking ${list.length} flagged ${list.length === 1 ? 'person' : 'people'}...`);
  } else {
    console.warn('No other match is visible to test the search with first -- carrying on, but treat the "gone" results with care.');
  }

  const gone = [], present = [], unsure = [];
  let n = 0;
  for (const p of list) {
    n++;
    const rows = await search(p.name);
    const exact = rows.some((r) => r.id === p.id);
    const sameName = rows.some((r) => r.id !== p.id && r.name && r.name.toLowerCase() === p.name.toLowerCase());
    if (exact) present.push(p.id);
    else if (sameName) unsure.push(p.id);
    else gone.push(p.id);
    console.log(`[${n}/${list.length}] ${p.name}: ${exact ? 'still there' : sameName ? 'only another match with that name came up -- unsure' : 'not found -- gone'}`);
    await randomDelay();
  }
  await setSearch(input, '');
  const json = JSON.stringify({ verified: { gone, present, unsure } }, null, 1);
  let copied = false;
  try { copy(json); copied = true; } catch (e) { /* not a real DevTools console */ }
  if (!copied) { try { await navigator.clipboard.writeText(json); copied = true; } catch (e) { /* no clipboard */ } }
  console.log(`${gone.length} gone, ${present.length} still there, ${unsure.length} unsure${copied ? ' -- copied' : ''}. Paste into the dashboard like any other batch.`);
  if (!copied) console.log(json);
};

// The mirror image of tinderFindUnmatched: that one finds ids that
// VANISHED from the sidebar; this finds ids that are IN the sidebar but
// the DASHBOARD never got. Deliberately compares against the dashboard's
// own known match ids (window.__dashKnownIds, appended by its "Copy
// bulk-import snippet" button, same as tinderSeedDone/tinderSeedStale) --
// NOT this browser's doneVersions, which is exactly the skip-list that
// hides a profile an early run scraped while its panel hadn't finished
// rendering (marked done, empty, never sent on). Same full-scroll-both-
// tabs sweep tinderFindUnmatched uses, since collectAllCandidates() alone
// doesn't scroll. Output feeds straight into tinderReextract().
window.tinderFindMissing = async (knownIds) => {
  const known = new Set((knownIds || window.__dashKnownIds || []).filter(Boolean));
  if (!known.size) { console.warn('tinderFindMissing needs the dashboard\'s known match ids -- copy the bulk-import snippet from the dashboard (it appends them), or pass an array: tinderFindMissing(["id1","id2"]).'); return; }

  async function scrollListFully(ul) {
    if (!ul) return;
    let box = ul;
    while (box && !(box.scrollHeight > box.clientHeight + 50 && box.clientHeight > 100)) box = box.parentElement;
    if (!box) return;
    let lastHeight = -1, stable = 0;
    for (let i = 0; i < 200 && stable < 3; i++) {
      box.scrollTop = box.scrollHeight;
      await new Promise((r) => setTimeout(r, 300));
      if (box.scrollHeight === lastHeight) stable++; else stable = 0;
      lastHeight = box.scrollHeight;
    }
  }

  const startedOnTab = findTabButton('Matches')?.getAttribute('aria-selected') === 'true' ? 'Matches'
    : findTabButton('Messages')?.getAttribute('aria-selected') === 'true' ? 'Messages' : null;
  console.log('Scrolling both lists to load your whole match history first -- this can take a while...');
  const visible = new Map();
  await switchToTab('Matches');
  await scrollListFully(document.querySelector('ul[aria-label="Your matches"]'));
  collectCandidates().forEach((r) => visible.set(r.id, r.name));
  await switchToTab('Messages');
  await scrollListFully(document.querySelector('ul[aria-label="Your recent messages"]'));
  collectCandidates().forEach((r) => visible.set(r.id, r.name));
  if (startedOnTab) await switchToTab(startedOnTab);

  const missing = [...visible.keys()].filter((id) => !known.has(id));
  if (!missing.length) {
    console.log(`${visible.size} matches visible, all ${known.size} known to the dashboard -- nothing missing.`);
    return;
  }
  missing.forEach((id) => console.log(`  missing: ${visible.get(id) || '(no name)'} -- ${id}`));
  const json = JSON.stringify({ reextract: missing }, null, 1);
  let copied = false;
  try { copy(json); copied = true; } catch (e) { /* not a real DevTools console */ }
  if (!copied) { try { await navigator.clipboard.writeText(json); copied = true; } catch (e) { /* no clipboard */ } }
  console.log(`${missing.length} match${missing.length === 1 ? '' : 'es'} in your sidebar the dashboard has never stored${copied ? ' (copied)' : ''}. Pull them now with:\n\n  tinderReextract(${JSON.stringify(missing)})\n\nthen paste the downloaded file into the dashboard as usual.`);
  if (!copied) console.log(json);
};

// Re-extracts a SPECIFIC list of match ids -- unlike tinderBulkImport()
// (todo = not yet marked done) or tinderCatchUp() (todo = active
// conversations since a date), this is driven entirely by an explicit id
// list. Built for exactly the situation a fix like the virtualized-photo-
// carousel one creates: cross-referencing already-downloaded batch files
// for whoever's best-ever scrape still came back suspiciously thin is far
// more targeted than re-running a broad sweep over everyone. Reuses
// extractProfile/findLinkById/waitForProfile/randomDelay/downloadChunk --
// same per-row shape tinderBulkImport() itself uses, just fed an explicit
// list instead of filtering by doneVersions.
window.tinderReextract = async (ids) => {
  const idSet = new Set((ids || []).filter(Boolean));
  if (!idSet.size) { console.warn('tinderReextract needs an array of match ids -- e.g. tinderReextract(["abc123", "def456"])'); return; }

  console.log(`Re-extracting ${candidates.length} targeted profile${candidates.length === 1 ? '' : 's'}. This takes a while -- real delays are the point.`);
  const doneVersions = loadDoneVersions();
  const profiles = [];
  const chunkState = { chunkIndex: 0, totalSaved: 0 };
  try {
    for (let i = 0; i < candidates.length; i++) {
      const row = candidates[i];
      console.log(`[${i + 1}/${candidates.length}] ${row.name}...`);
      const link = await findLinkById(row.id);

// Primes doneVersions from ids the DASHBOARD already knows about (its own
// connections' tinderMatchId), not just whatever THIS browser has
// personally scraped before -- localStorage only remembers a browser's
// own runs, so a fresh browser/profile, or one with site data cleared,
// makes every match look brand-new again even for someone who's been in
// the dashboard for months, paying the full anti-bot delay hundreds of
// times over for nothing new. No profile opens, no delays -- marking done
// is instant; the only cost is comparing against whatever's currently
// scrolled into the sidebar (collectCandidates()), same completeness
// caveat tinderFindUnmatched() already documents. The dashboard's own
// "Copy bulk-import snippet" button appends a call to this automatically,
// so a normal paste seeds it with zero extra typing -- callable by hand
// too, e.g. after importing profiles from somewhere this browser never
// ran the snippet against.
//
// KNOWN EDGE CASE: this stamps ids at the CURRENT SCRIPT_VERSION, trusting
// that whatever the dashboard already has for them is fine -- it has no
// way to know whether that data actually reflects the current version's
// extraction logic or an older, since-fixed one (there's no per-
// connection "captured at script version N" record, only
// tinderLastScrapedAt, a timestamp). So a SCRIPT_VERSION bump meant to
// force everyone to be re-checked (per the comment above SCRIPT_VERSION)
// gets silently defeated the next time this seeds someone at the NEW
// version without them having actually been re-scraped. tinderCatchUp()'s
// Messages-tab sweep doesn't have this problem -- it never consults
// doneVersions at all, it just re-opens everyone with activity since a
// date -- so THAT (not a SCRIPT_VERSION bump + tinderBulkImport) is the
// reliable way to force a real re-verification after a fix like this one.
window.tinderSeedDone = (ids) => {
  const idSet = new Set((ids || []).filter(Boolean));
  const doneVersions = loadDoneVersions();
  let newlyMarked = 0;
  idSet.forEach((id) => { if (!isDoneWith(doneVersions, id)) newlyMarked++; doneVersions[id] = SCRIPT_VERSION; });
  saveDoneVersions(doneVersions);
  const currentIds = new Set(collectCandidates().map((r) => r.id));
  const missing = [...idSet].filter((id) => !currentIds.has(id));
  console.log(`Seeded ${idSet.size} known match id${idSet.size === 1 ? '' : 's'} (${newlyMarked} new to this browser) -- tinderBulkImport()/tinderCatchUp() will skip all of them now.`);
  if (missing.length) console.log(`${missing.length} of those aren't in the currently-visible sidebar -- scroll both lists down to load everyone before trusting this as "unmatched": ${missing.join(', ')}`);
};

// Runs automatically at the tail of tinderBulkImport()/tinderCatchUp(),
// after their own primary work -- closes the one gap neither of those (nor
// tinderFindUnmatched) can see: a match you've never messaged can still
// quietly change its bio or photos, with nothing here ever noticing, since
// the Matches-tab sweep only ever checks "have I seen this id before",
// never re-opening an already-known profile. Re-opening EVERY already-
// known profile to catch that would defeat the entire point of skip-
// tracking, so this instead re-checks just the `n` longest-untouched ones
// each run -- a slow rotation through everyone over many runs, not a
// one-shot fix.
//
// Its own separate checkpoint file (a distinct name — see downloadChunk's
// filePrefix), deliberately NOT folded into the primary run's own count or
// output: explicitly fine to skip pasting it in on any given day (per the
// request that shaped this) -- whoever doesn't get refreshed today just
// carries over and gets picked again next run, same as a normal missed day
// costs nothing.
async function staleSweepTail(n, chunkSize) {
  // Checkpoints its own file this often too, same reasoning as the primary
  // run's own CHUNK_SIZE -- confirmed as a real gap: this used to hold
  // everyone in memory and write ONE file only at the very end, so a big
  // n (or a manual Ctrl+C, or a memory-related crash left running
  // overnight) lost the ENTIRE stale-refresh batch, not just the last
  // partial chunk the way the primary run was already protected. Defaults
  // lower than the primary run's 25 -- a stale-refresh session is more
  // likely to be a large, unattended, or manually-interrupted one.
  const CHUNK_SIZE = chunkSize || 15;
  const staleMap = loadStaleMap();
  const ids = Object.keys(staleMap);
  if (!ids.length) return; // never seeded (e.g. an old copy of this snippet, pasted by hand) -- nothing to act on
  const currentById = new Map((await collectAllCandidates()).map((r) => [r.id, r]));
  const videoBacklog = loadVideoBacklog();
  const ranked = ids
    .filter((id) => currentById.has(id))
    // Video-backlog ids first (they haven't been re-scraped since video
    // capture existed), then everyone else -- date-sorted within each
    // group, '' (never scraped) still first.
    .sort((a, b) => {
      const va = videoBacklog.has(a) ? 0 : 1, vb = videoBacklog.has(b) ? 0 : 1;
      return va - vb || (staleMap[a] || '').localeCompare(staleMap[b] || '');
    });
  const batch = ranked.slice(0, n);
  if (!batch.length) { console.log('Stale-refresh: nothing visible to refresh right now.'); return; }
  console.log(`Stale-refresh: re-checking the ${batch.length} longest-untouched already-known profile${batch.length === 1 ? '' : 's'} -- separate from the run above, its own file, no rush.`);
  const profiles = [];
  const chunkState = { chunkIndex: 0, totalSaved: 0 };
  for (let i = 0; i < batch.length; i++) {
    const row = currentById.get(batch[i]);
    console.log(`[stale ${i + 1}/${batch.length}] ${row.name}...`);
    const link = await findLinkById(row.id);
    if (!link) { console.warn(`Stale-refresh: couldn't find ${row.name} any more -- skipped.`); continue; }
    link.click();
    const loaded = await waitForProfile(row.name, 8000);
    if (!loaded) { console.warn(`Stale-refresh: ${row.name}'s profile didn't load in time -- skipped.`); continue; }
    await new Promise((r) => setTimeout(r, 500));
    try {
      const extracted = await extractProfile(row.name);
      extracted.matchId = row.id;
      profiles.push(extracted);
    } catch (err) {
      console.warn(`Stale-refresh: extraction failed for ${row.name}: ${err.message} -- skipped.`);
    }
    if (profiles.length >= CHUNK_SIZE) downloadChunk(profiles.splice(0, profiles.length), false, chunkState, 'tinder-stale-refresh');
    if (i < batch.length - 1) await randomDelay();
  }
  // Whatever's left is the tail end that hasn't hit a CHUNK_SIZE checkpoint
  // yet -- downloadChunk() itself no-ops on an empty list, so this is safe
  // to call even when the loop above already flushed everything exactly on
  // a chunk boundary.
  downloadChunk(profiles, false, chunkState, 'tinder-stale-refresh');
  console.log(`Stale-refresh: ${chunkState.totalSaved} of ${batch.length} saved across ${chunkState.chunkIndex} file${chunkState.chunkIndex === 1 ? '' : 's'} in Downloads -- paste in whenever, no rush; anyone skipped today just gets picked again another run.`);
}

// Standalone entry point for a large, dedicated stale-refresh session --
// e.g. tinderStaleRefresh(200) left running overnight -- rather than only
// ever getting a small batch as a tail-add-on to tinderBulkImport()/
// tinderCatchUp(). Matters for the exact overlap this was built to avoid:
// the dashboard's own "who's most overdue" ranking only updates once a
// stale-refresh file is actually pasted back in and saved, so invoking
// the SMALL tail-add-on repeatedly in one sitting (25, then another 25,
// before pasting either in) reselects the same longest-untouched people
// every time rather than rotating through more of the list. One longer
// call, its own frequent checkpoints protecting it, covers more ground
// without that problem. n defaults to 25 (same as the tail-add-on's own
// default); chunkSize defaults to 15.
window.tinderStaleRefresh = (n, chunkSize) => staleSweepTail(n ?? 25, chunkSize ?? 15);

(async () => {
  // Accumulates across pages: run on /albums, then on /people, then paste.
  // Bump whenever the capture/scroll logic below changes -- forces
  // window.__dash to start clean instead of quietly carrying forward
  // whatever an OLDER version of this script already captured (including
  // anything it captured wrong, or never caught at all) across repeated
  // runs in the same tab. Same idea as SCRIPT_VERSION in the Tinder
  // import snippet.
  const SNIPPET_VERSION = 4; // /people match is now by aria-label presence, not a base64-alignment-fragile href substring that missed roughly half the tiles
  window.__dash = (window.__dash && window.__dash.v === SNIPPET_VERSION) ? window.__dash : { v: SNIPPET_VERSION, albums: new Map(), people: new Set() };
  const onAlbums = location.pathname.includes('album');
  const grab = () => {
    // Verified against the live page: each album has TWO anchors sharing an
    // href (a cover tile and a text tile), aria-label is absent, and the
    // cover is a CSS background-image on a descendant, not an img. So both
    // anchors are merged by URL, keeping whichever piece each one carries.
    // A SHARED album's tile links to /share/<id>?key=... instead of
    // /album/<id> -- confirmed live from a real Shared-album tile's
    // outerHTML, and the reason every shared album was silently invisible
    // to this snippet, not a scroll/timing miss like the others.
    document.querySelectorAll('a[href*="/album/"], a[href*="/share/"]').forEach(a => {
      // The /share/ link's ?key=... IS the access token -- stripping it
      // (like the plain query-string trim below) would save a URL that
      // 403s the moment it's opened later. /album/ links carry no such
      // token, so they keep the existing trim (whatever transient params
      // Google sometimes appends there aren't part of the link's identity).
      const url = /\/share\//.test(a.href) ? a.href : a.href.split('?')[0];
      const lines = (a.innerText || '').split('\n').map(s => s.trim()).filter(Boolean);
      let cover = '';
      for (const el of a.querySelectorAll('*')) {
        const b = getComputedStyle(el).backgroundImage;
        // Mid-transition this can be a cross-fade of two layers, e.g.
        // -fade(url("A") 8.8%, url("B") ...) — not a plain url("..."), so a
        // fixed-offset slice grabbed the whole thing as garbage. Pull out
        // the first real url(...) instead, wherever it's wrapped.
        const m = b && b.match(/url\("([^"]+)"\)/);
        if (m && m[1].includes('usercontent')) { cover = m[1]; break; }
      }
      // The grid requests tiny thumbnails (often 24px); ask for a usable one.
      if (cover) cover = cover.replace(/=s\d+/, '=s400');
      // A shared album's second line reads "47 items · Shared", not just
      // "47 items" -- the original $-anchored regex only ever matched a
      // private album's plain count line, so a shared album's count (and,
      // worse, its title-exclusion check) silently missed every time.
      const ITEMS_RE = /^\d+\s*items?\b/i;
      const titleLine = lines.find(l => l.toLowerCase() !== 'no items' && l.toLowerCase() !== 'more options' && !ITEMS_RE.test(l));
      const countLine = lines.find(l => ITEMS_RE.test(l));
      const prev = window.__dash.albums.get(url) || {};
      window.__dash.albums.set(url, {
        url,
        title: prev.title || titleLine || '',
        count: prev.count || (countLine ? parseInt(countLine, 10) : 0),
        cover: prev.cover || cover,
      });
    });
    // The old /QUYxUWlw/ check on a.href was a base64 substring match on a
    // length-prefixed protobuf blob -- it only ever matched by coincidence,
    // when the preceding name's byte length happened to leave the token
    // 3-byte-aligned. A shorter or longer name shifts that alignment and
    // produces a DIFFERENT base64 rendering of the exact same underlying
    // token (confirmed against two real tiles: "Phil White" matched,
    // "Tamara White" -- one character shorter -- didn't, same page, same
    // kind of tile). Requiring an aria-label instead is both more reliable
    // and simpler: every real person tile carries one (verified against
    // several real tiles), and it's what a person's name actually lives in
    // regardless of how the href happens to encode.
    document.querySelectorAll('a[href*="/search/"][aria-label]').forEach(a => {
      const t = (a.getAttribute('aria-label') || '').trim();
      if (t && !/^Photo|\d{1,2}:\d{2}/.test(t)) window.__dash.people.add(t);
    });
  };
  const box = [...document.querySelectorAll('div')]
    .filter(d => d.scrollHeight > d.clientHeight + 500 && d.clientHeight > 200)
    .sort((a,b) => b.scrollHeight - a.scrollHeight)[0] || document.scrollingElement;
  const countNow = () => onAlbums ? window.__dash.albums.size : window.__dash.people.size;
  // Two things changed here from a plain fixed-step scroll-and-grab:
  //
  // 1. grab() runs TWICE per stop, a beat apart, not once. A tile's name
  //    label can populate a moment after the tile itself lands in the DOM
  //    (an async render, not a layout one) -- a single grab() right after
  //    scrolling sampled plenty of tiles mid-render with a blank label,
  //    confirmed live on /people as a "select, miss, select, miss" pattern
  //    even though every one of those tiles was clearly a named person on
  //    screen a moment later.
  //
  // 2. On /people specifically (autoStop below), the sweep stops once
  //    several steps in a row add no one new. Named people cluster at the
  //    top with no gaps -- past them is Google's much longer "Others"
  //    section this app has no use for, which used to make the whole
  //    sweep take minutes for nothing. Albums have no such shape (a real
  //    album can be anywhere on the page), so autoStop never applies there.
  const sweep = async (from, to, step, autoStop) => {
    let flat = 0;
    for (let y = from; step > 0 ? y < to : y > to; y += step) {
      const before = countNow();
      grab();
      box.scrollTop = y;
      await new Promise(r => setTimeout(r, 260));
      grab();
      await new Promise(r => setTimeout(r, 220));
      if (autoStop) {
        if (countNow() === before) flat++; else flat = 0;
        if (flat >= 6) break;
      }
    }
    grab();
  };
  box.scrollTop = 0;
  await new Promise(r => setTimeout(r, 400));
  await sweep(0, box.scrollHeight, 120, !onAlbums);
  // Second pass, back upward, over the SAME span the first pass actually
  // covered (not all the way from scrollHeight down to 0) -- same
  // "virtualized out of the grid again before grab() caught it" reasoning
  // that motivated a two-pass sweep in the first place, just bounded to
  // wherever there was actually anything worth finding.
  const reachedY = box.scrollTop;
  await new Promise(r => setTimeout(r, 300));
  await sweep(reachedY, 0, -120, false);
  const out = {
    albums: [...window.__dash.albums.values()].filter(a => a.title),
    people: [...window.__dash.people],
  };
  if (onAlbums && out.albums.length === 0) {
    // Google changes this markup from time to time. Rather than fail
    // silently, show what IS on the page so the selector can be corrected.
    const sample = [...document.querySelectorAll('a')].slice(0, 40)
      .map(a => a.getAttribute('href')).filter(Boolean);
    console.warn('No albums matched. Paste this back to Claude:', JSON.stringify(sample));
  }

  // A cover URL only resolves for whoever is logged in at the moment it's
  // fetched — the dashboard is a different site with no way to borrow this
  // session, so a bare URL 403s the instant it's embedded there, no matter
  // how fresh. Fetching each cover HERE, while still authenticated, and
  // embedding the actual bytes as a data URI sidesteps that for good. A few
  // at a time so it doesn't hammer Google; anything that fails (CORS, a
  // slow connection, whatever) just keeps its plain URL — never worse than
  // today, only ever better.
  if (onAlbums) {
    const withCover = out.albums.filter(a => a.cover && a.cover.startsWith('http'));
    if (withCover.length) {
      console.log(`Fetching ${withCover.length} cover images while logged in — give this a few seconds…`);
      const queue = [...withCover];
      const embedOne = async (a) => {
        try {
          const res = await fetch(a.cover, { credentials: 'include' });
          if (!res.ok) throw new Error(`HTTP ${res.status}`);
          const blob = await res.blob();
          a.cover = await new Promise((resolve, reject) => {
            const reader = new FileReader();
            reader.onload = () => resolve(reader.result);
            reader.onerror = reject;
            reader.readAsDataURL(blob);
          });
        } catch (e) { /* leave the plain URL — no worse than before */ }
      };
      const worker = async () => { while (queue.length) await embedOne(queue.shift()); };
      await Promise.all(Array.from({ length: 5 }, worker));
      const embedded = withCover.filter(a => a.cover.startsWith('data:')).length;
      console.log(`Embedded ${embedded} of ${withCover.length} covers` + (embedded < withCover.length ? ' — the rest kept their link and will show as expired in the dashboard.' : '.'));
    }
  }

  const json = JSON.stringify(out, null, 1);
  // copy() is a DevTools convenience global, injected only into a console
  // opened directly in that panel — it throws ReferenceError anywhere else
  // (a docked/undocked console reattached differently, remote debugging,
  // some extensions' console proxies). Clipboard API needs a secure context
  // AND focus, neither guaranteed right after pasting into DevTools, so this
  // tries three ways and always leaves the JSON visible either way.
  let copied = false;
  try { copy(json); copied = true; } catch (e) { /* not in a real DevTools console */ }
  if (!copied) {
    try { await navigator.clipboard.writeText(json); copied = true; } catch (e) { /* no clipboard permission/focus */ }
  }
  console.log(`${copied ? 'Copied' : 'Could not auto-copy — select the JSON below and copy it manually:'} `
    + `${out.albums.length} albums and ${out.people.length} faces.`
    + (onAlbums ? ' Now run this again on /people to spot people with no album.' : ''));
  if (!copied) console.log(json);
})();

How do I record a switch bonus and whether it has been paid?

How do I mark which account I could switch away from next?

Letting income & owner reports




How do I set up someone who owes me a share of a listing?


    

  1. Go to Settings → Finances → Airbnb listings and find the listing's row.
    2. 

  2. Choose the person under Owner, or type a name in the box marked "or a name" if they aren't a connection. An owner called Phil counts as you: no balance owed and no report.
    3. 

  3. Set Share %: the part of each stay's takings the owner owes you.
    4. 

  4. To change the split from a future date, or to limit it, open + schedule a change, set the date, the %, and optionally Cap £, then press Add. The cap is the most an owner owes you in one calendar month, across all their bookings.
    5. 



A stay on a listing with no owner never shows in Letting income at all. A change that has already taken effect can't be removed; a future one has an ×.







How does a stay turn into money owed?


    

  1. In the Airbnb panel on Overview, type what the stay earned in the booking's Income £ box. If you're signed in to Google, Sync at the top of the panel also fills in the guest name and the payout from Airbnb's confirmation emails for bookings that don't have a guest name yet.
    2. 

  2. Choose Airbnb or Other on the booking if it didn't come through Airbnb.
    3. 

  3. On the checkout day, a row appears under the owner's name in Letting income, dated that day, showing the guest, the stay's total takings and the owner's share (Share %, limited by any cap). Their balance goes up by the share.
    4. 

  4. Stays still to come, or finished but waiting on an income figure, are listed in Upcoming / awaiting payout beneath the ledger as a preview. They don't count until they become rows.
    5. 



Rows are created when you open the dashboard, and straight away when you type income on a stay that has already ended. If you leave the dashboard open across checkout, reload to see it. Deleting such a row with its × (you are asked to confirm) also clears the income on the booking so it stays deleted; type the income again to charge it again.







How do I record a payment, a write-off or money from before I started?


    

  1. Under the ledger, pick who it's for, choose the kind, type the Amount, check the date, add a note, and press Add.
    2. 

  2. Payment: money that really moved. Enter a negative amount when they pay you, a positive one when you hand them money.
    3. 

  3. Adjustment: changes the balance with no money moving, such as writing something off. To clear a balance, add the negative of it.
    4. 

  4. Cancellation: a payout for a stay that never happened. The amount is exactly what the balance moves by, so apply the share yourself.
    5. 

  5. Earned (historic): what a listing took before you used the dashboard. Type the gross takings; the share is applied for you. Nights and Check-in date are optional but make the charts accurate.
    6. 



Pick the kind for what happened, not for the sign, because months later the kind is the only record of why the balance moved. Every row's date is editable, and its note shows the stay it came from.







What are the other kinds of row in an owner's ledger?


    

  1. Cancellation and Refund rows also come from Airbnb's emails when you press Sync in the Airbnb panel. A cancellation payout is added with the owner's share and dated the day after check-in. A refund you sent a guest is added as a negative row dated the day Airbnb emailed it.
    2. 

  2. Any refund Sync can't match to an owner is listed in the Airbnb panel under Guest refunds waiting to be assigned. Choose who it's charged to and press Post, or press × to leave it off the ledger. Setting the listing's owner in Settings and pressing Sync again also posts it.
    3. 

  3. Monthly cap rows (an adjustment) and Loan interest rows are worked out for you and can't be edited or deleted.
    4. 








How does the monthly cap work?


    

  1. Set a Cap £ on a listing's share rule (see the first job in this section).
    2. 

  2. Each stay is limited to the cap on its own. If the owner's shares for one month (by each row's date) add up to more than the cap, a Monthly cap £N, YYYY-MM adjustment row takes off the excess so the month totals no more than the cap.
    3.

    3.

    4.

How is interest worked out?


    

  1. Each day, interest runs on what's lent to you minus what that owner owes you on the Airbnb ledger that day (never below zero). The rate is a yearly % divided by 365. A tranche stops earning on its Repay date.
    2. 

  2. The Airbnb balance is set against the tranche due back soonest first, so the longer-dated loans are what stay outstanding. Each tranche earns its own rate on its own remaining part.
    3. 

  3. If you already owe the owner through the ledger (their balance is negative), that amount is charged interest as well, at the average rate.
    4. 

  4. Under the lender's name the panel shows what's lent today, what they owe you on the Airbnb ledger, what's interest-bearing right now, interest so far this month and interest posted to date.
    5. 








When does the interest reach the ledger?


    

  1. When the dashboard opens on or after the 1st of a month, the previous month's interest is added to that owner's Letting income ledger as a negative Interest row dated the 1st, titled "Loan interest, <Month Year>". It reduces what they owe you.
    2. 

  2. Missed months (the dashboard wasn't opened) are all posted next time, oldest first, each one counted after the one before it.
    3. 

  3. Once interest is on the ledger it counts towards later months' interest too, so interest compounds monthly.
    4. 








I changed or removed a tranche. How do I fix the interest already posted?


    

  1. Press Recalculate interest and confirm. It removes every automatic interest row and works them out again from the loans as they are now.
    2.

Paying a tranche back early isn't a separate action: set its Repay date to the day it was repaid, then Recalculate. The loan sums themselves aren't kept in the ledger, so if you settle by netting against Airbnb money, record that as a Payment row.

  2. Press Parse ingredients under the Ingredients box. The app splits each line into name, form, quantity and unit. The status shows what it is doing.
    3. 

  3. Press Analyse ingredients (it parses first if you haven't). Each ingredient it hasn't seen before is looked up one at a time ("Assessing onion… (2/9)"). Ingredients seen in earlier recipes are reused, so later recipes are quicker.
    4. 

  4. Press Show diet analysis to read the result: tags such as High protein or Low calorie, FODMAP per component, glycemic load, allergens, vegetarian/vegan/kosher/halal facts, and macros.
    5. 



If you edit the ingredients afterwards, a link appears: Ingredients changed since last parse — re-parse. The analysis is only as good as the parse, so press Show parsed ingredients and check the name, form, quantity and unit on each line. Fix any that were misread (for example "2 cloves garlic" read as teaspoons). Tick the box beside a line to mark it optional, which leaves it out of the totals and lists it under "Optional additions" instead.







What do I do when a line says its unit doesn't match?


    

  1. The warning appears under the parsed line, for example when the recipe says "1 large onion" and the reference amount is in grams. The totals leave that line out until it is sorted.
    2. 

  2. Press the Ask AI how many grams 1 … is link, or type the figure yourself in the box beside it and press Save.
    3. 

  3. The ingredient remembers the answer, so the same unit never needs asking again.
    4. 








How do I see what a swap or a smaller amount would do?


    

  1. In the diet analysis, each ingredient with a FODMAP, glycemic, allergen or diet-flag result has a drop-down.
    2. 

  2. Choose Substitute to use one of its listed alternatives, Use less to cut it down (to low for that ingredient alone, or for the whole recipe), or Drop from analysis.
    3. 

  3. The totals and tags change straight away. Choosing a substitute the app hasn't looked up before takes a moment, once.
    4. 

  4. For Use less, the amount appears in a box you can adjust.
    5. 



These choices are saved with the recipe, so they are still there after a reload. Setting an ingredient back to "as written" clears it, and so does re-reading the ingredients (Parse), since the lines may be numbered differently afterwards. To turn a set of swaps into a real recipe, see the next question.







How do I keep an adjusted version of a recipe?


    

  1. Make your swaps as above. A Make it like this box lists them in plain words.
    2. 

  2. Press Save as a new recipe with these changes. The app rewrites the ingredients and instructions to match and adds the result as a new recipe, opened and scrolled into view.
    3. 

  3. The new recipe says "Adapted from" with a link back to the original, which is left untouched.
    4. 



The copy keeps the Course and tags but not the Gluten, Dairy or FODMAP choices (set them again once you've checked the new ingredients) and starts with no ratings. The new recipe is analysed straight away for its own diet figures (this uses AI, and says so if your key is missing).








The ingredient reference and diet settings



How do I correct an ingredient the app got wrong?


    

  1. In the diet analysis, press the Wrong allergens/FODMAP/etc? Edit … link under the ingredient. This opens it in Ingredient Reference.
    2. 

  2. Change what's wrong: the reference amount, macros, the grams of each FODMAP carbohydrate, glycemic index, antioxidant value, allergens, the vegetarian/halal-type facts, substitutes, and how much one of another unit weighs ("medium" = 110 g).
    3. 

  3. Press Save. Every recipe using that ingredient picks up the new figures. A saved edit is marked "edited" and is never overwritten by a later AI check.
    4. 



Changing the reference amount does not rescale the other figures, which stay as typed but now apply to the new amount, so check them too. Ingredient Reference is empty until a recipe has been analysed.







How do I merge two names for the same ingredient?


    

  1. In Ingredient Reference, press Show ingredient reference, then Merge into… on the duplicate (for example "scallion").
    2. 

  2. Start typing the entry to keep (for example "spring onion"), pick it from the list that appears, and confirm. Recipes using the old name now use the kept entry's figures, and the old entry is removed.
    3. 

  3. To undo, press undo beside the name under Merged names. That name is then assessed afresh the next time it is used.
    4. 



Only the kept entry's figures survive a merge, so merge into the one you trust. The × on a row removes an entry; the next analysis that needs it asks AI again.







How do I hide diet sections I don't need?


    

  1. Open Menu — diet interests in Settings (or press the gear in the Recipes panel heading).
    2. 

  2. Click a chip to switch it off or on: Macros, FODMAP, Diabetic (glycemic load), Allergens, and Kosher / halal / vegetarian / vegan.
    3. 



This only changes what is shown. Every ingredient is still fully assessed, so switching a section back on shows what was already there, with no new AI check.







How do I change what counts as High protein, Low calorie and so on?


    

  1. Open Menu — diet tag thresholds in Settings.
    2. 

  2. Type new cutoffs for High protein (% of energy from protein), Low calorie (kcal per serving or under), High fibre (g per serving) and High antioxidant (mmol per serving). A blank or invalid entry goes back to the default.
    3. 

  3. Tags on every recipe and the Diet chips update straight away.
    4. 



The three per-serving tags only apply to recipes that have Servings set.

How do I log an idea?

    2. 

  2. Tick a step when it is done, or press × beside it to remove it.

How do I see an idea's tasks on the Tasks tab?


    

  1. Open Tasks. The default view leaves out business ideas so they don't bury everyday tasks.
    2. 

  2. Press the Business ideas chip under Also show to include them, or just click the link on the idea's row to jump straight to its Project.
    3. 








What if I delete the Project or task later?


    

  1. The idea goes back to normal by itself: the link disappears, and its steps list and Turn into buttons return so you can start again.
    2. 



It works the other way round too: deleting an idea does not delete a Project or task you made from it, and the confirmation says so. Delete that in Tasks as well if you want it gone.

See the Nudges guide for how reminders are chosen and how often they show.

Health




The Health tab shows your steps, sleep, heart rate, weight and similar numbers in one place, and charts any of them against each other. The numbers come from three places: your phone (through a bridge app), a Renpho smart scale, and Samsung Health screenshots.




Getting data in



How do I get my phone's steps, sleep and heart rate onto the Health tab?


    

  1. Make sure live sync is set up first (the sync URL and secret in Settings). The Health tab reads from the same server.
    2. 

  2. Upload health.php next to sync.php on your server, using the same secret. The setup steps are in Settings → Health data.
    3. 

  3. On your phone, install a Health Connect bridge app (for example HC Webhook), grant it the data you want, and point its webhook at your health.php address. If the app has no field for a secret, add ?secret= followed by your secret to the end of the address.
    4. 

  4. Back on the Health tab, press ↻ Sync & parse. The line beside the button says how many synced entries it read and how many days that made. A new row appears in the Daily activity table for each day.
    5. 



Sync & parse reads everything the server holds and rebuilds the Daily activity table from scratch each time, so it is safe to press as often as you like. Nothing arrives until the bridge app has sent at least one sync, so an empty table straight after setup is normal.







How do I check that the bridge app is really sending?


    

  1. Open Settings → Health data and press Check for data.
    2. 

  2. It shows how many recent entries the server holds and when the latest arrived, followed by the raw contents of the newest five. If it says nothing has been received, the problem is on the phone or the webhook address, not in the dashboard.
    3. 

  3. Press Sync & parse on the Health tab if the raw entries are there but the table is not.
    4. 



Once a week the app also checks the feed by itself. If nothing has arrived for 36 hours, or the newest entry has no field it recognises, the Health sync row in Settings → Site health turns red and says why. The same check runs whenever you press Sync & parse.







How do I add my Renpho scale readings?


    

  1. In the Renpho app, export your data as a CSV file.
    2. 

  2. Share that file to the dashboard from your phone's share sheet, or press + Capture files in Capture Inbox and pick it.
    3. 

  3. The dashboard recognises it as a Renpho export by its contents and files it straight into Body composition (Renpho). A banner tells you how many days of readings it imported. There is no import button to press.
    4. 



A Renpho export always contains your whole history, so sharing it again is safe: a day already there is replaced, never duplicated. If you weigh yourself more than once in a day, the latest weigh-in is the one kept. Readings the scale only partly captured (weight and BMI, say) show a dash for the rest.







How do I add HRV, sleeping heart rate, AGEs or antioxidant readings?


    

  1. In the Samsung Health app, open the 7-day chart you want (HRV, Sleeping HR, AGEs index or Antioxidant index) and take a screenshot. Tapping a day first makes its exact value show, which makes the reading more accurate.
    2. 

  2. Share the screenshot to the dashboard. If its file name contains "Samsung Health" (a normal Android screenshot of that app does), it is read straight away and the banner reports what was found.
    3. 

  3. If the screenshot stays in Capture Inbox instead, tick it and press Extract wellness data.
    4. 

  4. Check the new row in Wellness (Samsung Health) against the screenshot before you rely on it. To correct a wrong figure, click it, type the right number and press OK (leave it blank to clear it); the × at the end of a row deletes that whole day.
    5. 



The reading is done by AI from the picture, so it needs an Anthropic key in Settings. A ~ in front of a number means it was worked out from where the dot sits on the chart, not from a printed number. A figure you have already confirmed (a printed number, with no ~) is never replaced by a later estimate for the same day. A picture that is not one of the four charts is turned down with a message and left in the inbox.








Reading the tables



How do I read the three tables?


    

  1. Daily activity: one row per day from the bridge app, with steps, distance, calories, exercise, sleep, heart rate (lowest, average, highest), oxygen, weight and body fat. A dash means that figure was not sent that day.
    2. 

  2. Body composition (Renpho): weight, BMI, body fat, muscle mass, visceral fat and metabolic age from the scale.
    3. 

  3. Wellness (Samsung Health): HRV, sleeping heart rate, antioxidant index and AGEs index, with Samsung's own grade in brackets where it showed one.
    4. 

  4. Hover over a Sleep figure in Daily activity to see how it splits into stages.
    5. 



Sleeping heart rate lives only in the Wellness table. Samsung does not pass it to Health Connect, so it never reaches the Daily activity heart-rate columns, which are the all-day figures.







How do I see older days?


    

  1. By default each table shows individual days for the last month, then one averaged row per month back to a year, per quarter back to five years, and per year beyond that. The averaged rows are shaded.
    2. 

  2. Tick Show full daily history to see every day as its own row, in all three tables at once. Untick it to go back.
    3. 



Nothing is ever deleted by the summary view. Ticking the box shows the same days you already had.








The Trends chart



How do I compare two measurements?


    

  1. Find the Trends chart. It opens with weight and HRV already on it.
    2. 

  2. Press a + button under the chart to add a measurement (steps, distance, calories, exercise, sleep, oxygen, body fat, muscle mass, BMI, body water and so on). They can come from any of the three sources.
    3. 

  3. Press the × on a name in the key above the buttons to take it off.
    4. 

  4. Press 1M, 3M, 6M, 1Y, 5Y or All to change how far back it looks.
    5. 

  5. Drag across the chart to zoom into those dates, then press Reset zoom to come back out. The period buttons (1M, 3M… All) show which one is in use; after a drag-zoom none is highlighted.
    6. 

  6. Hover (or touch) the chart to see every measurement's value for that date.
    7. 



Only the first two measurements you pick get a labelled scale (one on each side). Any others are stretched to fit the same height, so read their actual values from the hover box or the figure at the end of the line, not from the scales. Where the bridge app and the scale both record weight, there are separate "Weight (Health Connect)" and "Weight (scale)" lines.








Health nudges



When does the dashboard comment on my health numbers?


    

  1. Once the Daily activity table has data, the Nudges panel on Overview can mention three things: an average of under six hours' sleep across your last logged nights, a weight change of a kilogram or more since your previous weigh-in (at least three days apart, from the phone or the scale), and no exercise logged for a whole week.
    2. 

  2. A nudge is only a prompt. Press it to come to the Health tab and look at the figures behind it.
    3. 



Heart rate and oxygen are left out of nudges on purpose, and the sleep one uses the Daily activity table only. The weight one also counts Renpho scale weigh-ins (the scale wins when both recorded the same day). See Nudges in this guide for how nudges work in general.

Mail




The Mail panel on the Overview tab shows the emails you care about, found by searches you set up, and lets you turn any of them into a task, a trip leg or a date idea with one tap. It only reads your Gmail: it never sends, deletes or moves anything. You need to be signed in to Google (the bar at the top of Overview) for it to load.




Choosing which emails show up



How do I get emails into the Mail panel?


    

  1. Open Settings → Mail searches and press Add search.
    2. 

  2. In the first dropdown choose what to look for: Starred, From, To, Subject contains, Contains (a word anywhere in the email) or Gmail query (anything Gmail's own search box understands). Except for Starred, type the value in the box beside it, for example airbnb.com.
    3. 

  3. Optionally set Max days (only emails from the last N days) and Max results (how many to show). Leave them blank for no day limit and the default number.
    4. 

  4. Go to the Mail panel and press Refresh mail. Each search appears as its own heading with its matching emails underneath.
    5. 



Each search is saved and follows you to your other devices. For anything fancier than a word or two (a Gmail label, OR, leaving a word out with a leading -, an exact phrase in quotes) choose Gmail query and type it exactly as you would in Gmail.






How do I change how many emails each search shows?


    

  1. For one search, type a number in its Max results box in Mail searches.
    2. 

  2. For every search that is left blank, change the default in Default max results, when a mail search's is blank.
    3. 



The number counts emails you can still act on. Emails you have already turned into a task, trip leg or date idea do not use it up; they move to a folded line instead (see What happens after I act on an email? below).






The same email matches two of my searches. Which heading does it appear under?


    

  1. It appears once, under the first search in the list that finds it. Searches are checked from the top of Mail searches down.
    2. 

  2. To make the other search win, move it up with the ↑ at the end of its row (or the one above it down with ↓).
    3. 







How do I group several searches under one heading?


    

  1. Open Settings → Mail topics and press Add topic. Name it, for example "Travel".
    2. 

  2. In Mail searches, set each search's Topic dropdown to it.
    3. 

  3. Refresh the Mail panel. Those searches now share one heading, with the newest email first. A search with Topic left on "— none —" keeps its own heading.
    4. 



A topic's heading no longer says "last N days", because its searches may each have a different limit. The number of emails it shows is the sum of its searches' Max results.






How do I choose which buttons show on a topic's emails?


    

  1. In Mail topics, tick up to three actions in that topic's row. A fourth tick unticks itself.
    2. 

  2. Those buttons sit directly on every email under that topic. Everything else is still one tap away under ⋯ Other actions.
    3. 



An email under a search with no topic shows every action under ⋯ Other actions and none directly. Give the search a topic if you want quick buttons.






How often does Mail refresh?


    

  1. When you open the app it refreshes by itself if it has not run in the last 6 hours (and you are signed in to Google).
    2. 

  2. Press Refresh mail any time to look again now. The line beside it says when it last updated and how many emails were handled automatically.
    3. 

  3. To change the interval or switch it off, use Settings → Scheduled syncs.
    4. 



If it says to sign in to Google, press the top of Overview link in the message to go to the sign-in bar, sign in, and press Refresh mail again.








Reading and clearing the list



How do I read an email?


    

  1. Tap the sender or subject of a row. The email opens in a window inside the app.
    2.

How do I make an email turn itself into a task, event or trip leg?

About this panel: what runs automatically

When an item is added, the dashboard looks up its poster and, for anything with a TMDb id, where it streams. A series with a link also gets its TVDB id looked up quietly, one at a time. Rows added while you were offline fix themselves the next time you open the tab. Recommendation sources are checked on their own weekly or monthly timers while the dashboard is open, not on a fixed clock.


Nothing here is ever downloaded, monitored or added to Plex without you pressing a button. The only automatic changes to a row are the status becoming Available after a Plex match or a Get… route, and the identifiers, poster and streaming tags being filled in.











Settings basics




Settings is organised in three tiers, all collapsible: a coloured group (Account & sync, Mail, AI features...) holds several items, and the odd item holds its own sub-groups below that — so only what you're actually looking at needs to be open. The pill row at the top of the Settings tab jumps straight to a group.


Sync: Account & sync is where your data gets between devices — a self-hosted server (your own URL + secret, the main path this app is built around) or a Google Drive backup. Connections additionally gets its own lighter per-record sync once that's set up, running alongside the whole-document sync rather than instead of it.


API keys: a TMDb key (free) powers film/TV/catalogue lookups across Media and the recommendations check; an Anthropic key powers every AI feature — Smart capture, photo/screenshot import, title resolution, and the rest. Both live under AI features, stored only on this device.


Backups: Advanced → export/import a complete copy of your data as a file, independent of whichever sync method you're using.
