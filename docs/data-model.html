Findings

Ordered by how much they can hurt. Each one cites what the live data showed.

High A stay has no stable identity, and its record is deleted when it ends

An Airbnb booking is created from a calendar feed with a fresh random id. When the stay finishes, or vanishes from the feed, that reservation is deleted. A thin copy goes into airbnbPastStays (no id, matched by listing + dates) or airbnbCancelledStays. Anything that held the old id is left pointing at nothing.

  • lettingLedger.reservationId: 4 of 5 references dangle.
  • airbnbKeys.forReservationId: 2 of 2 dangle.
  • Income is stored twice: on the reservation (income, 8 of 10) and as 29 earned ledger rows. None of the 10 live reservations has a ledger row for the same listing and check-in, so the two records cannot be joined.
  • Two stays on the same listing with the same dates collapse into one past-stay record.

Fix. One stays collection. The id never changes and the row is never deleted; it moves through booked, completed, cancelled. Amendments are kept as revisions on the stay. Past and cancelled stays become views. Ledger rows, keys and cleaning events hold stayId.

Done in v734. airbnbReservations is now the one stay list with a status; the feed sync and background refresh mark stays completed or cancelled instead of deleting them. The past and cancelled side lists were folded in, and three stays deleted before past stays were kept were rebuilt from their ledger rows, so no ledger reference dangles. A duplicate accrual (the same 2-night stay charged twice, £97.11 owner share) was removed, and accrual rows now take their id from the stay so a second device can't charge it again. Editing a charged stay's income updates its ledger row.

Added in v739. Duplicate stays (same room and dates, from two devices adding one feed event or Airbnb giving a booking a second calendar id) are merged on every load into one stay, keeping the calendar ids as altUids so the feed never adds it again; stays added from the feed take their id from the listing and calendar id, so two devices write the same record.

Added in v740. A booking code belongs to one booking: the guest-name email sync skips an email whose code is already on another stay (it matched only by arrival day, and copied one booking's name, payout and code onto the same dates on a second listing), and a load-time check clears a code and the details copied with it from any later holder.

Added in v741. A feed stay is "unconfirmed" until a confirmation email, a name or an income vouches for it (derived, no new field): Airbnb marks dates "Reserved" for an enquiry it is holding as well as for a booking. An unconfirmed stay shows a badge, gets no nudges, and if its dates drop off the feed before it starts and nothing refers to it, it is forgotten instead of being recorded as a cancelled booking.

Added in v744. Booking dates come from the inbox: the Airbnb sync reads every "Reservation confirmed" email (they go back to April 2024; each is dated the day the booking was made) and sets confirmedOn on a stay with none, or bookedOn on an old income entry in the ledger that has no stay record, when exactly one fits the arrival date and first name. It runs at most once a day (prefs.airbnbBookingDatesCheckedOn). Stays the Airbnb migration rebuilt no longer claim their checkout date as the booking date. The Nights booked chart shows nights with no booking date as a shaded band instead of hiding the comparison.

Added in v746. A Letting income row kept the guest, a sentence about it and (for a stay) the room all in one note, and the screen guessed the split. Rows now have guest (a person) and description (what happened) as fields, filled for every existing row on load by one function that reads an old note; note is unchanged because refund and cancellation matching still read it. The room comes from listingId.

Added in v749. A ledger row can carry bookedOn (the day the booking was made) when it has no stay record behind it, such as an older cancellation or income entry. The list under the Nights booked chart shows the bookings with no booking date and takes a date for each, written to the stay's confirmedOn or the ledger row's bookedOn. The inbox backfill also covers cancellation entries.

Added in v753. bookingRequests: every Airbnb "Pending: Reservation Request" and "Enquiry for" email becomes a record (guest, review count, city, listing from the email's rooms id matched to the ICS link, dates, party size, nightly rate and payout for a request, HM code or Airbnb thread id), including the ones never booked. decision is set when a stay with its code, or the same room, dates and guest, appears (reservationId), or not-booked once it lapses. prefs.bookingEvaluator holds the booking evaluator's starting assumptions, including per-room settings keyed by room. The checkout clean in the net night rate is now shared between rooms turned over the same day.

Added in v759. Letting income entries can carry confirmationCode (Airbnb's HM code), filled by the Airbnb earnings CSV import (Letting income → Import Airbnb earnings), which also fills startDate, nights, bookedOn and listingId on older entries and confirmationCode/confirmedOn/income on stays, only where blank. A booking request whose code is on an income entry counts as having become a stay.

Added in v761. A booking request can be marked decision: 'direct' (it was booked direct instead), with directEntryId = led:<income entry id> or res:<stay id>, set automatically when a direct stay in the same room overlaps it under the same guest name, or picked by hand. prefs.bookingEvaluator.unavailable lists periods a room wasn't offered, left out of the occupancy the evaluator calibrates to.

Added in v764. No stored fields changed. The booking evaluator now simulates only the free stretch of the request's room between the bookings either side of it (the dates the decision can change), shows the rest of the calendar as one projected scenario shared by every future, and lets each row of its Accept/Reject table open to the pieces it is made of.

Added in v765. bookingProjections: on request, the booking model simulates every room's free nights from today to the end of the month after next and saves one projection per day (per void: expected income, expected nights, a 1-in-10 range and a chance for each night; per month: totals and the expected cumulative nights booked by arrival day; one representative scenario; the assumptions used). The Letting charts (occupancy timeline, pace chart, Income by month, the occupancy bars on the night-rate charts) draw the latest one as hatched or dashed additions, hidden by prefs.showProjection.

High Vouchers are loyalty readings that were copied out

A loyalty reading can be a points balance or a voucher. The kind is stored in loyaltyLabelKinds, keyed by the program id and the reading's display label (27 rows, no id). 45 of 382 readings are voucher-kind. Confirming one copies it into vouchers, and each side then points at the other.

  • Two-way link: loyaltyBalances.voucherId and vouchers.sourceLoyaltyReadingIds. One voucherId dangles. 25 readings are marked skipped, so the same voucher reading is decided twice over time.
  • Both sides carry expiry and reference. The amount is a number plus a free-text unit on a reading (9 spellings: Avios, points, £, miles, €, status points, ...) and a free-text string on a voucher (£9.99, EUR9, 99 with no currency).
  • 4 of 15 vouchers have no source reading at all, so some are hand-entered and some are derived.

Fix. Keep readings as the history. Add one entitlements concept (voucher, credit, upgrade) with a single direction of reference to its source reading, a numeric amount and a currency or unit enum, and a status of active, used, expired.

Done in v736. The link runs one way: vouchers.sourceLoyaltyReadingIds. loyaltyBalances.voucherId was dropped (382 rows, 1 dangling) and a reading now looks its voucher up. Vouchers have a numeric amount and a unit (GBP, EUR, points, Avios, miles, nights, other), entered with a number box and a dropdown; value is now display text built from them. 10 of 15 values were parsed; Mastercard "70" and Tesco Clubcard "68" need a unit set by hand. Not done: a separate entitlements collection (vouchers already play that role).

High "Provider" is a plain string in five places

The same company is typed as text on vouchers, loyalty programs, subscriptions, finance accounts (bank) and cashback keys ("provider|merchant"). Each copy has its own logoUrl. A migration (providersConsolidated) unified the pick-list, but the data still stores strings, so a rename in one place changes nothing in the others.

  • 7 voucher providers, 14 loyalty providers, 7 subscription providers, 20 banks. 5 of the 7 voucher providers are also loyalty programs.
  • You already guessed this overlap. It is wider than vouchers: any company you hold points, a card, a subscription and a voucher with is four unrelated records.

Fix. A providers registry (id, name, logo, kinds). The other collections hold providerId.

Done in v738. New providers (id, name, logoUrl, aliases): 39 entries for 71 records. Vouchers, loyalty programs, subscriptions and bank accounts hold providerId. The text field stays as the displayed name and is relinked on every load, so an edit can never leave a stale id. A record's own logo still wins; otherwise the provider's is shown. Settings → Finances → Providers lists each provider with what uses it (each a link back) and renames or merges it everywhere; a merged name is kept as an alias. Annual perks still match a bank by text.

Medium Airbnb relations rest on text and on ids that do not merge

  • A listing is matched to calendar events by a text prefix in the event title (ES-P, Dbl-Z, ...). Two of five listings have no feed at all.
  • Cleaners are bare strings (airbnbCleaners). Cleaning events are {date, name}. Un-assigning a clean is stored as the string "reservationId:edge".
  • The ledger owner is called ownerKey and holds a connection id. Listings call the same thing ownerConnectionId.
  • None of the Airbnb collections is in the per-record sync. Four of them have no ids (airbnbPastStays, airbnbCleanerEvents, airbnbCleanerBlocks, airbnbCleaners), so a two-device edit cannot be merged by id and the server copy wins.
  • Domain data sits in the settings blob: prefs.airbnbRefundsSeen / Done / Pending, lettingTaxByOwner, airbnbCleaningCost.

Done in v734. All eight Airbnb collections are in the per-record store (shadow mode; switching over stays a Settings step). Stays now have stable ids, so cleaning un-assignments and key assignments no longer dangle; the unused forReservationId on keys was removed. Kept on purpose: the listing prefix (it is how the shared calendar marks external bookings; there is no id to use), the ownerKey name on ledger rows (a rename would change nothing you see), and the refund "seen" lists in prefs (processing state; a later move into the mail ledger).

Medium Connections hold the same fact in two shapes

  • Chat: 217 connections still have the legacy chatLog string although all 597 are flagged as migrated to identities[].chatLog. chatLogWhatsApp and chatLogTelegram are empty everywhere.
  • Tinder id: the scalar tinderMatchId duplicates the first identity row. 3 people have more than one match id.
  • Photos: photoId and photoIds[]. One record has a cover that is not in its own list.
  • Telegram: telegramChatId and telegramUsername (0% filled) duplicate the identity row.
  • Duplicates: 76 groups of connections share a name. Some are real different people, some are the same person.
  • Transient UI state is saved on the record: createdJustNow (60% of records), tinderPhotoRetryNeeded (57%).

Done in v737. The connection-level chatLog, chatLogWhatsApp and chatLogTelegram are gone: 199 were already on a chat row and were dropped, 18 were moved onto one (16 of those people had no chat row, so their old chats were not showing anywhere). The Today list and the "has chatted" check read chat rows only. createdJustNow is no longer saved (the Tinder review keeps it in memory) and was removed from 368 records. The one cover photo missing from its own list was added. Corrected: tinderPhotoRetryNeeded is a deliberate warning flag, and telegramChatId is the family bot's chat id, not a copy of an identity row. Left for you: the 76 same-name groups need a person to judge; the merge picker handles each pair. tinderMatchId stays as the first match id.

Medium At least ten ways to say "hidden" or "done"

A stage value, a boolean, a timestamp, a separate dismissed list, a snooze date, a family flag and age-based deletion are all used. See Archive & hide. Each feature re-implements its own filter, so a new list has to remember which idiom applies.

Medium Structured facts stored as prose

Height has four text formats, distance is "≤N/M", age is a string next to an "as of" date, and the Tinder bio is appended to notes on 347 connections (average note 371 characters, longest 2,602). Details in Text as data.

Low Smaller drift

  • Twelve boolean …Seeded / …Backfilled flags sit in the document as migration bookkeeping (loyaltyProgramsSeededV2 to V6, providersConsolidated, ...). A single schemaVersion would replace them.
  • Mixed-type fields: financeAccounts.fundingAmount and airbnbListings.sharePct hold both strings and numbers.
  • subscriptions.cost (string, 0% filled) and subscriptions.amount (number, 57%) are the same thing. mediaItems.tvdbId duplicates externalIds.tvdb.
  • plannerEntries is polymorphic: kind plus five nullable foreign keys (trip, connection, activity, task, recipe).
  • mailLedger.produced lists {kind, id} pairs, a reference with no target collection fixed.
  • The synced document carries derived and cached data: 203 media candidates, per-recipe parsed ingredient data with a signature, ingredient "stale" flags.

How the areas connect

Arrows run from the record that holds the reference to the record it points at. Only cross-area references are drawn.

Airbnb and letting

You suspected this model is not robust. It is the weakest area, mainly because one real-world thing, a stay, is spread over four collections with different keys.

Where a stay lives over its life

Money. Before income counts, the amount sits on the stay as expectedPayout (with paidOn). Once recognised it is posted as one ledger entry carrying the stayId, and the stay's income is the sum of its entries, never a stored second copy. Refunds, price changes and cancellations are further entries (deltas), so there is no "two halves" of one payment. Settlement rows with the owner (payments, interest, monthly-cap adjustments) share the ledger but have no stay.

Amendments. A changed booking is a STAY_REVISION, not a status. The stay stays booked, its current dates are updated, and the old dates are kept in the revision, so a chart can use the dates that applied on any given day. Open question: whether Airbnb keeps the same feed uid when dates change; the next real amendment will show it. moved is no longer a status: movedFromListingId records a hand move between rooms.

The existing feed uid plus listing is the natural key used to avoid duplicates on each sync. The confirmation code (the HM… string in every Airbnb host email) is the key that ties an email to its stay exactly, and gives a direct link to the reservation page.

Built already (v733). Reservations now carry confirmationCode, revisions and payoutCheck. When the feed changes the dates of a stay that has a payout, the old dates are kept as a revision and the stay is flagged "payout to check" with a link to the Airbnb reservation page. Airbnb's "Reservation updated" email has no dates or amounts, so the new payout is entered by hand; it is never estimated. These fields are copied onto past and cancelled stays too.

Vouchers and loyalty

Your guess holds: they overlap on the provider, on the expiry and reference, and on the reading itself.

Also separate today: Marriott points (marriottAvailability.pointsBalance) and cashback network balances (they appear as £ readings in loyaltyBalances, while the rates sit in cashbackRates). The label-to-kind table disappears once a reading carries its own kind.

Suggested order of work

Each step is independent and reversible. Steps 1 to 3 give the most robustness for the least change.

  1. Give Airbnb stays a permanent id.Medium. Keep the existing reservation id as the stay id from now on, stop deleting at checkout (set a status instead), and migrate past and cancelled stays into the same list. Repoint ledger, key and cleaning references. Do this before any further Airbnb features.
  2. Add a providers registry.Small to medium. Seed from the existing unified pick-list, add providerId next to the text on vouchers, programs, subscriptions and accounts, then stop writing the text.
  3. Make vouchers one direction from readings.Medium. Add kind on a reading, an entitlements shape with numeric amount and a currency or unit enum, and drop the label-to-kind table and the reverse link.
  4. Put the Airbnb collections in the per-record sync and give every list an id.Small. Past stays, cleaner events, blocks and cleaners get ids, and the five Airbnb collections join the finance set.
  5. Type the loose fields.Small each: number-only sharePct and fundingAmount, remove subscriptions.cost, unit enum, heightCm, a distance range, E.164 phone.
  6. One archive convention.Medium and cross-cutting. archivedAt plus reason, one visibility helper, and migrate lists one at a time starting with vouchers and offers.
  7. Replace the seeded flags with a schema version.Small. One number and an ordered list of migrations.
  8. Retire the duplicate connection fields.Small after a parity check: legacy chatLog (217), tinderMatchId scalar, Telegram id fields, and the saved UI flags.
  9. Reference clean-up helpers.Small. One delete helper per record type that unlinks or cascades, so a deleted task, trip or voucher cannot leave a dead id. The 7 dangling references found today (of about 760) would stop growing.

Limits of this review: counts come from one device's copy of the document read on 4 November 2026. Server-side tables (records.php) and fields that are always empty in your data but used by code paths you have not hit were reviewed from code only.

Keeping this current

Two files sit in the repository next to the app, so the page can be checked against the real data instead of trusted.

  • docs/data-model.json lists every top-level key by area and every reference worth checking.
  • docs/check-model.js reports keys the model does not know, keys that no longer exist, and dangling references. Run it on the live site:
const r = await import('./docs/check-model.js').then((m) => m.checkModel());
console.table(r.dangling); r.undocumented
  • Rule in the repository's CLAUDE.md: any change to state.js (new key, new reference field, new factory, new archive field) updates the JSON and the matching diagram, runs the check, and republishes this page.
  • The diagrams are plain text in this page, so a changed relationship is a small, reviewable edit.
